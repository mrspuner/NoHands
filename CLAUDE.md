# NoHands

Менюбар-приложение для macOS: голосовой ввод текста в любое приложение по хоткею плюс автоматическая запись, расшифровка и архивирование созвонов.

Проект личный, на одного пользователя. Дистрибуции нет, значит не нужны нотаризация, автообновления, онбординг и обратная совместимость.

@docs/DESIGN.md
@docs/DECISIONS.md

## Среда

Mac mini M4, 16 ГБ памяти, 256 ГБ SSD. Микрофон внешний, USB. Машина всегда включена и в сети.

## Стек

- Swift, SwiftUI, менюбар через `NSStatusItem`
- WhisperKit — локальное распознавание
- FluidAudio — диаризация и эмбеддинги голосов
- GRDB — SQLite для отпечатков голосов
- ScreenCaptureKit — системный звук, AVAudioEngine — микрофон
- ElevenLabs Scribe v2 API, Anthropic API (Haiku)

Зависимости только через Swift Package Manager. Новые зависимости не добавляем без явного обсуждения — каждая тянет за собой обновления и лицензии.

## Секреты

Репозиторий публичный. В гит не попадает ничего из перечисленного:

- ключи API — только Keychain, в коде читаются через обёртку в `Core/`
- `~/Meetings` — транскрипты и аудио живут вне репозитория
- база отпечатков голосов
- веса моделей

Если для работы понадобился ключ — не хардкодь и не клади в `.env` внутри репо, спрашивай.

## Журнал решений

`docs/DECISIONS.md` дополняется, когда принято архитектурное решение или отвергнут вариант. Записи не редактируются задним числом: если решение изменилось, добавляется новая запись со ссылкой на старую.

Правки в `docs/` коммитятся и пушатся сразу, отдельным коммитом, не дожидаясь готовности кода. Причина: решения обсуждаются в чате Claude.ai, который читает файлы из публичного репозитория по ссылке. Пока правка не в origin, вторая половина работы идёт по устаревшему контексту.

Код пушится по готовности, промежуточные состояния коммитить не нужно.

## Рабочий процесс

Работа идёт через скиллы Superpowers. Скилл вызывается до действия, а не после: он задаёт способ работы, а не оформляет уже сделанное.

- Новая функциональность или изменение поведения — `superpowers:brainstorming` до любого кода
- Многошаговая задача — `superpowers:writing-plans`, затем `superpowers:executing-plans`
- Реализация — `superpowers:test-driven-development`, тест раньше кода
- Баг, падающий тест, непонятное поведение — `superpowers:systematic-debugging` до предложения починки
- Прежде чем сказать «работает» — `superpowers:verification-before-completion`: сначала прогон, потом утверждение
- Ревью — `superpowers:requesting-code-review` и `superpowers:receiving-code-review`

Исключение — механические правки по прямой инструкции: переименование, перемещение файлов, коммит. Там процессный скилл ничего не добавляет.

## Порядок работ

Фазы идут строго последовательно, потому что каждая добавляет своё системное разрешение macOS, и при одновременной отладке нескольких непонятно, что именно отвалилось.

1. **Фаза 0** — ядро: протокол `Transcriber`, обе реализации, запись микрофона. Проверка качества на реальных русских записях до всякого UI.
2. **Фаза 1** — диктовка: хоткей fn, Scribe, постобработка, вставка текста.
3. **Фаза 2** — созвоны: ScreenCaptureKit, две дорожки, очередь, диаризация, генерация markdown.

Внутри фазы не забегаем вперёд: не пишем задел под будущие фазы, не абстрагируем то, что пока имеет одну реализацию.

## Чего не делать

- Не добавлять функциональность из раздела «не цели» в `docs/DESIGN.md`
- Не изобретать обобщённые слои под гипотетические сценарии
- Не заменять внятную ошибку на молчаливый фолбэк: если распознавание не удалось, приложение должно сказать об этом, а не подсунуть пустую строку
- Не логировать содержимое транскриптов и распознанного текста
